# Pod 桥接协议 v1

| 项 | 值 |
| --- | --- |
| 版本 | v1（2026-11-19） |
| 性质 | **共享契约**：服务端与客户端各自实现，任何一方都不能单方面改 |
| 服务端 | `dsh-podbridge`（DSH 插件） |
| 客户端 | 任何实现本协议的聊天软件（参考实现：Pod App） |

> **名字的由来**：Pod 是一群鲸共居的集体。
> 现在是一人一 agent（一个 Pod），将来是多 agent 私聊与群聊（更多 Pod）。
> 协议从 v1 起就按"多会话"预留，不把单会话写死。

> 这份文档是桥接与聊天软件之间**唯一**的耦合点。
> 两侧的实现文档（《dsh-podbridge 设计需求》《Pod App 设计需求》）都只引用本文件，
> 不互相引用对方的内部设计。

---

## 一、范围

只做三件事：**握手、发消息、收消息**。

明确不做（也不属于本协议）：

| 不做 | 归属 |
|---|---|
| UI 渲染、气泡、未读、通知 | 客户端内部 |
| 会话绑定、聚合窗口、分段标记 | 服务端内部 |
| 消息状态机（发送中/已读） | 双方都不做 |
| 附件/图片/语音 | v2 |

---

## 一点五、协议**不**定义什么（边界）

这一条是为了防止桥接承担越来越多职责。协议只传**消息与文件**：

| 概念 | 归属 | 说明 |
|---|---|---|
| 联系人、昵称、头像 | **客户端本地** | 桥接不发送、不存储、不关心 |
| 聊天背景、主题 | 客户端本地 | 同上 |
| 表情包 | 客户端本地 + 发送时上传 | 桥接只把它当普通文件 |
| 会话名称 | 客户端本地命名 | 桥接不透传 DSH 会话标题 |
| `chatId` | 协议已有字段 | v1 固定 `private`；客户端当不透明标识 |

判断标准：**能只存本地、且不影响收发的东西，一律不进协议。**

另外，协议**不承担消息持久化**：服务端不需要保存聊天历史，
客户端自行在本机保存；服务端只维护一个短期缓冲用于断线补拉，容量与保留时间由实现决定。

## 二、传输

| 项 | 约定 |
|---|---|
| 通道 | **SSE（`text/event-stream`）下行 + POST 上行** |
| 地址 | `GET http://<host>:<port>/events?since=&token=`；上行用 `POST /send` |
| 编码 | 每个 SSE 事件一个 JSON（`data: {...}\n\n`） |
| 帧大小上限 | 单条文本消息 4000 字符 |
| 心跳 | 服务端每 15 秒发一行注释 `: keep-alive`（SSE 注释不触发事件） |
| 超时 | 连接空闲由代理决定；客户端断线后指数退避重连 |

**为什么不用 WebSocket**：最初设计是 WS，但本地 link 安装的插件解析不到 `ws` 依赖
（profile 里没有该包）。用 Node 自带的 http 实现 SSE + POST 语义完全够用，
且浏览器 `EventSource`/fetch 都原生支持。**协议语义与 WS 版一致**，只是线格式不同。

## 三、配对

客户端首次连接前，需要用一个一次性配对码换取长期 token。

```
POST /pair
Content-Type: application/json

{ "code": "482913", "deviceName": "My Phone" }

→ 200 { "ok": true, "token": "<长期凭证>", "chatId": "private", "sessionLabel": "..." }
→ 401 { "ok": false, "error": "invalid_code" | "code_expired" | "code_used" | "no_code" }

| 错误码 | 含义 |
|---|---|
| `invalid_code` | 配对码不正确 |
| `code_expired` | 配对码已过期 |
| `code_used` | 配对码已被使用（一次性） |
| `no_code` | 服务端还没生成过配对码 |

**客户端应把错误码翻译成人话**（见客户端设计 10·12），不要直接把 `invalid_code` 甩给用户。
```

| 规则 | 说明 |
|---|---|
| 配对码 | 6 位数字，**5 分钟内有效，用一次即失效** |
| token | 长期有效，直到管理员在设置页吊销 |
| 多设备 | 同一 token 可被多端使用（v1 不做设备管理） |

---

### 3.1 谁负责什么（避免误以为是"某个桥接插件的私有机制"）

| 层 | 归属 | 说明 |
|---|---|---|
| 配对码怎么生成、在哪显示、长什么样 | **实现自由** | 设置页、命令行、配置文件都行 |
| `POST /pair` 的请求/响应与错误码 | **协议规定** | 任何想服务 Pod App 的桥接都必须提供 |
| token 怎么存、怎么吊销 | **实现自由** | 协议不定义吊销语义 |

也就是说：**配对流程本身是协议的一部分，不是 dsh-podbridge 的私有接口。**
换一个桥接实现，只要它提供 `POST /pair`，Pod App 一行不改就能配对。

### 3.2 备选：直接发放 token（v1.1 计划）

若某个桥接不想实现 `POST /pair`，也可以由管理员直接给出 token，让客户端手动填写：

| 方式 | 客户端需要 | 状态 |
|---|---|---|
| A. 配对码 → `POST /pair` | 默认流程 | ✅ v1 已实现 |
| B. 管理员给 token，手动填写 | 设置页多一个输入框 | ⬜ 计划中（v1.1） |

两种方式的 token 语义完全相同；B 只是省掉交换这一步。

## 四、握手

SSE 建连即完成握手：`GET /events?since=<seq>&token=<token>`。

成功时服务端先发一个 `welcome` 事件，再按顺序补发 `since` 之后的消息：

```
event stream:
data: {"type":"welcome","chatId":"private","lastSeq":135,"serverTime":1795000000000}
data: {"type":"msg","message":{...}}
data: {"type":"msg","message":{...}}
: keep-alive
```

- 鉴权失败 → `401`，不建立流
- `since` 缺失或为 0 → 服务端回放最近若干条
- 版本不匹配 → 服务端在 `welcome` 里带 `version`，客户端自行判断

## 五、帧定义

### 5.1 上行（客户端 → 服务端）

上行不是帧，而是普通 HTTP 请求：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/send` | `{clientMsgId, text, attachments?}`；`text` ≤ 4000 字符 |
| GET | `/history?beforeSeq=&limit=` | 分页历史（`limit` ≤ 100） |
| POST | `/pair` | 配对换 token |
| POST | `/upload` | 上传文件 |

### 5.2 下行（服务端 → 客户端）

SSE 事件的 JSON：

| type | 字段 | 说明 |
|---|---|---|
| `welcome` | `chatId, lastSeq, serverTime` | 建连后第一帧 |
| `msg` | `message: {seq, role, text, at, attachments?}` | **唯一的消息事件** |
| `closed` | `reason` | 服务端主动断开（重载/吊销凭证），客户端应停止重连 |

> 注意：**没有** `hello` / `ping` / `pong` / `history` 帧。
> 握手即建连；心跳是 SSE 注释行（`: keep-alive`），客户端可忽略；
> 历史用 `GET /history` 主动拉。

### 5.3 `message` 结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `chatId` | string | 所属会话。**v1 恒为 `"private"`**；多会话时用于区分 |
| `seq` | number | **服务端分配，单调递增**（按 chatId 各自递增）。客户端不得自造 |
| `role` | `"user"` | `"agent"` | `"system"` | `user` 是回显，`agent` 是模型回复，`system` 是服务端提示 |
| `text` | string | 正文（纯附件消息可为空串） |
| `at` | number | 毫秒时间戳 |
| `attachments` | array? | 文件元数据，见 5.5.3 |

**一个回合可能产生多条 `msg`**（`role=agent`，`seq` 连续）。
客户端应连续渲染，不需要把它们合并。

## 五点五、文件（v1.1）

客户端与服务端之间只传两个新接口 + 消息里的一个字段，不涉及实现细节。

### 5.5.1 上传

```
POST /upload?token=<token>
Headers: x-file-name: <encodeURIComponent(原名)>
Body:    原始字节（不是 multipart）

200 → { ok:true, id, name, size, mime }
413 → { ok:false, error:'file_too_large', maxMB }
401 → { ok:false, error:'invalid_token' }
```

`id` 由服务端生成，客户端只负责带回引用。

### 5.5.2 下载

```
GET /files/<id>?token=<token>   ← 浏览器 <img> 带不了自定义头，必须支持查询串 token

200 → 文件字节；Content-Type 为服务端判定的类型
404 → { ok:false, error:'file_not_found' }
```

### 5.5.3 消息字段

上行 `send` 与下行 `msg` 都可能有：

```json
"attachments": [
  { "id": "20261119-ab12cd", "name": "cat.png", "size": 123456, "mime": "image/png" }
]
```

| 规则 | 说明 |
|---|---|
| `id` 必须来自 `/upload` 或服务端下发 | 客户端**不得**用本地路径拼 id |
| 上行 `text` 可以为空 | 只发附件是合法的 |
| 下行 `attachments` 可能只有附件没有文本 | 客户端要能渲染空文本消息 |
| 文件存哪、是否白名单、怎么生成 | **服务端实现自由**，协议不规定 |

### 5.5.4 客户端不关心的事

- 服务端把文件存到哪个目录
- 白名单与大小上限怎么配（只读 `413` 的错误信息来提示用户）
- agent 用什么工具发出文件
- **服务端怎么把文件推给客户端**（工具、管理端点、或别的机制）：协议只规定
  `msg.attachments` 的字段形状，不规定由哪个接口产生。
  换一个桥接实现，这条路径可能完全不同。

### 5.5.5 服务端保留多久（第三方实现必读）

客户端的取图逻辑是**两级**：

1. 先查本机文件库（`getClientFile(id)`）
2. 本地没有 → `GET /files/<id>?token=` 回服务端拉，成功且 ≤ 自动保存阈值就顺手落盘

这意味着 **`/files/<id>` 是"本地副本丢失后的唯一退路"**。因此：

| 服务端行为 | 后果 |
|---|---|
| 长期保留文件 | 客户端换设备、清缓存、换目录后都能自愈 ✅ |
| 只保留最近 N 天 | 超过 N 天的旧图在客户端会变成不可用 ❌ |
| 完全不落盘（内存中转） | 本机副本一删，历史附件全部失效 ❌ |
| 未实现 `/files/<id>` | 同上，且新发的图在本机存盘失败时也打不开 ❌ |

协议**不强制**保留策略（存储成本由实现方决定），但实现方必须知道这个代价。
建议至少与客户端自动保存阈值（默认 10 MB）配合：小文件客户端会自己留一份，
大文件只能靠服务端。

反过来说，客户端**不得假定**服务端永久保留：取不到时按 `404` 优雅降级，
显示"附件已失效"之类占位，不要当作致命错误。

## 六、顺序与补拉

> **客户端实现建议**：直接用 `since=0` 拉最近 50 条，靠去重键过滤重复。
> 不要拿"本地水位"当 `since`——服务端重启后编号可能变化，水位一旦对不上，
> 补拉会静默返回空，表现为"消息全收不到"。去重键建议 `seq + at + 文本前缀`，
> 只看 `seq` 会因编号重复而误判。

| 规则 | 说明 |
|---|---|
| `seq` 单调 | 客户端按 `seq` 排序，不依赖到达顺序 |
| 补拉 | 重连时 `GET /events?since=<本地最大 seq>`，服务端补发其后所有消息（客户端也可传 0 拉最近若干条） |
| 缺口 | 若服务端无法补发（超出保留窗口），发一条 `role=system` 的消息说明"部分历史缺失" |
| 保留窗口 | 服务端至少保留最近 1000 条 |

## 七、拒绝与提示

**协议里没有错误帧。** 服务端拒绝一条消息时，发一条 `role=system` 的消息说明原因：

```json
{ "type": "msg", "message": { "seq": 136, "role": "system", "text": "桥接已关闭，消息未投递", "at": 1795000000000 } }
```

| 场景 | system 文本示例 |
|---|---|
| 总开关关闭 | `桥接已关闭，消息未投递` |
| 绑定会话失效 | `绑定的会话不可用，请管理员处理` |
| 文本超长 | `消息超过 4000 字，未投递` |
| 触发限流 | `发送过于频繁，本条未投递` |

## 八、不保证的事（明确写出来）

| 不保证 | 原因 |
|---|---|
| **投递** | 没有回执机制，"发出去了"不等于"agent 收到了" |
| **不重复** | 服务端按 `clientMsgId` 做尽力去重，但不承诺端到端幂等 |
| **在线** | 断线即不可达；重连后靠 `seq` 补拉 |
| **实时** | 服务端可能有聚合窗口，消息不会立即到达 agent |

## 九、兼容规则

1. **未知帧忽略**（不报错、不断开）
2. **未知字段忽略**（便于双方独立演进）
3. 新增帧/字段属于**次版本**，不需要双方同时升级
4. 破坏性变更 → `version` 递增，服务端拒绝不兼容客户端（关闭码 `4002`）

---

## 九点五、动态：v1 不走协议，将来可能单向开放

Pod App 的「动态」页：**v1 由用户本人写，纯本地存储，不经过桥接**。

| 阶段 | 决定 |
|---|---|
| **v1** | 不传输、不提供工具；动态纯本地 |
| 将来 | 可能让 **agent 只写不读**（桥接提供写入工具 + 存储） |
| 读取 | **默认不开放**；若开放，必须显式分页 + 严格字符上限 |

**为什么写可以、读要克制**：写入是单向的、成本可控；读取会让累积的几百条动态一次性灌进上下文。

在开放之前，动态与桥接协议**完全无关**。

## 十、多会话预留（v1 不做，字段先留）

路线图上的下一步是「管理员与多个 agent 私聊」，之后是群聊。协议**不把单会话写死**：

| 字段 | v1 行为 | 将来 |
|---|---|---|
| `message.chatId` | 恒为 `"private"` | `"private:<agentId>"` / `"group:<id>"` |
| `send.chatId` | 可省略，默认 `"private"` | 必填 |
| `seq` | 全局一条序列 | **按 chatId 各自递增** |
| `since` 参数 | 单值 | 变成 `{chatId: seq}` 映射 |
| `welcome` | 单个 `chatId` | 返回会话列表 |

**v1 的实现只要保证 `chatId` 字段存在且恒为 `"private"` 即可**，
将来扩展不需要破坏性变更——客户端从 v1 起就按"消息带 chatId"来写。
