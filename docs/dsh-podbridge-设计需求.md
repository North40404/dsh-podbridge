# dsh-podbridge 设计需求

| 项 | 值 |
| --- | --- |
| 版本 | v0.1（草案，2026-11-18） |
| 定位 | 个人聊天软件 ↔ 本地 DSH 会话的**桥接插件** |
| 服务对象 | **Pod App**（个人聊天软件，见《Pod App 设计需求》） |
| 与定时任务类插件的关系 | **两条互不知道的线**：对方拥有触发路径，本插件拥有消息路径 |
| 放置位置 | `<目录>\dsh-podbridge`（新建总文件夹） |
| 硬约束 | **不复制 qq-bridge 的代码**；只借鉴其经验 |

> **为什么叫 podbridge**：Pod 是一群鲸共居的集体。
> 现在是一人一 agent，将来是多 agent 私聊与群聊——名字留了生长空间。

---

## 一、一句话定义

把「我」在自有聊天软件里发的一条消息，投进一个 DSH 会话；
把 DSH 会话的回复，原路发回聊天软件。

**不是** QQ 适配器，**不是** 多 agent 房间枢纽，**不是** 通用 IM 网关。

---

## 二、边界（明确不做什么）

### 2.1 与"触发类"插件的边界

| | 触发类插件 | 本插件 |
|---|---|---|
| 拥有 | **触发路径**（什么时候叫醒） | **消息路径**（人说了什么、怎么回） |
| 输入 | 时间 | 聊天消息 |
| 输出 | `sessionController.prompt("[Timer] …")` | `sessionController.prompt("[chat] …")` |

两者只共享一个事实：**都向同一个会话投递 prompt**。
除此之外互不感知——谁都不知道对方是否存在。

### 2.2 与 DSH 的边界

- 只用官方服务（`sessionController` / `workspaceController` / `webServer`），**不碰内部文件格式**
- 不改 DSH 的模型、会话、工具配置
- **绝不**用 `agent.inject` 之类的兜底写入（曾写坏过会话）

### 2.3 v1 明确不做

| 不做 | 原因 |
|---|---|
| 群聊 | 只是构想，且涉及多 agent 身份判定，另立设计 |
| 逐字流式 | 复杂度高（增量拼接/重试重置/断线续传），且手机网络最不稳定 |
| 附件/图片/语音 | v1 只做纯文本 |
| 工具审批、`ask_user_question` 作答 | 需要额外通道，v2 再议 |
| 多会话切换（同一个绑定下） | v1 只绑一个，管理员手动改绑 |
| 已读回执、输入中状态跨端同步 | 非核心 |

## 三、角色与数据流

```
手机 App / Windows 浏览器
      │  WebSocket（自有协议，带配对 token）
      ▼
┌─────────────────────────────────────────┐
│ dsh-podbridge（DSH Host 插件）              │
│  · 鉴权：token → 身份=用户               │
│  · 绑定：chatId(我们的聊天) → sessionId  │
│  · 入站：组装信封 → prompt(queue)        │
│  · 出站：session/event → 整条回复 → 推送  │
└─────────────────────────────────────────┘
      │  sessionController.prompt / 事件订阅
      ▼
   DSH 会话（管理员绑定的那一个）
```

### 3.1 入站（聊天 → DSH）

```
消息到达
 → 校验 token（失败 401，不投递）
 → 总开关关闭？（关闭则拒收并回固定提示，不投递）
 → 生成信封 {chatId, senderId, senderRole:'user', text, clientMsgId}
 → 幂等：clientMsgId 已处理过 → 直接返回成功，不重复投递
 → sessionController.prompt({ sessionId: 绑定会话, requestId: clientMsgId,
                              mode: 'queue', content: [{type:'text', text: 渲染后的信封}] })
```

**为什么用 `queue`**：宿主负责排队，回合进行中不会打断，也不需要桥接自己 `whenIdle` 阻塞。
（qqbot 用 `agent.followup` 必须自己等空闲，因为 followup 在回合中会 `turn/end=blocked`。）

### 3.2 出站（DSH → 聊天）

```
ctx.on('session/event')
 ├─ assistant/message → 取 content 里的 text 块 → 整条推给该轮来源 chat
 ├─ tool/call, tool/result → 可选：渲染成"正在执行…"状态
 └─ turn/end（reason） → 结束"思考中"
```

**不逐字**：只消费 `assistant/message`，不订阅 `agent/assistant-stream`。
理由：一次回复通常就是一个 step，收到即整条；逐字是将来可选增强。

**一轮一推**：`turn/end=completed` 时收尾；`aborted`/`error`/`blocked` 时按 reason 给用户一个可读状态。

### 3.3 出站分段（agent 打标）

一轮回复可以拆成**多个气泡**，由 **agent 自己决定**：在需要断开的地方独占一行写 `[[split]]`。

| 规则 | 说明 |
|---|---|
| 标记 | 独占一行、大小写不敏感；桥接据此切分，**从正文里剔除** |
| 代码块内 | ``` 围栏内的 `[[split]]` **不生效** |
| 未打标 | 整条一个气泡 |
| 单段过长 | 超过 `segmentMaxChars`（默认 2000）→ 按长度兜底拆 |
| 语义 | 分段只影响**显示**，仍然算同一轮 |

**给模型的约束**（写进系统提示）：

1. 默认：一条回复就是一个气泡
2. 想模拟真人连发的节奏时，用 `[[split]]` 拆成 **2~4 条**，不要更多
3. 每一段要能独立读懂，**不要拆成一两个字的碎片**
4. 代码、表格、长引用不要拆开

> 为什么按"节奏"而不是"话题"：日常聊天本来就是一连串短消息
>（"在的" / "我看看" / "找到了"），按话题约束会让模型几乎不敢分段。

### 3.4 入站聚合（窗口攒批）

同一聊天窗口的消息先进缓冲，满足**任一**条件就合并成一次提示词投递：

| 条件 | 默认 | 说明 |
|---|---|---|
| 静默窗口 `silenceSec` | **6 秒** | 每条新消息重置计时 |
| 窗口总时长 `maxWindowSec` | 15 秒 | 一直不停口也最多等 15 秒 |
| 攒满条数 `maxMsgs` | 10 条 | 攒满立即投递 |

投递时的渲染：

```
[chat] 用户连发 3 条（间隔 <6 秒）：
1. [表情: 偷笑]
2. 在吗
3. 帮我看看定时任务那边的日志
```

**为什么静默是 6 秒而不是 3 秒**：典型场景是"先发图片/表情，再打字"——
3 秒会在字还没打完时就把前半截投给 agent，等于白聚合。

**协议层的后果**：消息投递到会话最多晚 `silenceSec`（6 秒）。
**客户端如何呈现不归本插件管**——"…"气泡、超时、未读数全部是客户端自己的事。

### 3.5 回合正在跑时的新消息

**排队**（`prompt` 的 `queue` 模式），不插话。

- 复杂度最低，不会打断正在输出的回合
- 代价仅是 agent 回复变慢（要等前一轮跑完）

## 四、绑定模型

### 4.1 绑定关系

| 项 | 规则 |
|---|---|
| 私聊会话 | 绑定**一个** DSH 会话，**必填** |
| 群聊会话 | v1 不实现（见 2.3） |
| 选择器 | 列出所有会话，**过滤归档会话** |
| 归档判断 | 唯一来源 `workspaceController.follow()` baseline 帧的 `archivedSessionIds`；`list()` 本身不过滤 |

### 4.2 切换绑定

**前置条件：总开关必须处于关闭状态。**

理由：切换瞬间如果有回合在跑或消息在队列里，旧会话的回复会投递到新聊天、或新消息被投进旧会话。

切换时同时执行：

1. 清空待投递队列（未投递的消息一律丢弃，不留到新会话）
2. 重置该绑定的「当前轮来源」映射
3. 记录一条日志：`绑定从 X 切换到 Y`

### 4.3 总开关

| 状态 | 行为 |
|---|---|
| 开 | 正常收发 |
| 关 | **拒收**手机消息，回一条固定提示（"桥接已关闭"）；不投递、不入队 |

页面上总开关旁必须写明：**关闭后手机消息会被拒绝，不会暂存**。
（选择拒收而非暂存：关闭期间的消息通常已过时，暂存会让开关打开瞬间被旧消息轰炸。）

## 五、身份原则（本插件最重要的安全约束）

> **身份由服务端赋值，永远不从消息内容推断。**

| 环节 | 规则 |
|---|---|
| senderRole | 由 token 决定（`user`）；**用户正文里写"我是管理员"只是正文**，不改变 role |
| 信封 | 由桥接生成，用户输入**只作为 text 字段**参与，不参与拼接 |
| 动作校验 | 凡因身份而敏感的操作用服务端记录再校验一次，不依赖模型复述 |
| 来源自述 | 注入文本带结构化前缀 `[chat]`，与 tick 的 `[Timer]` 对称，让模型有稳定依据区分来源 |

**已知的 v1 混淆源**：`[Timer]` 注入与 `[chat]` 注入都表现为"用户消息"。当前只能靠前缀区分——这是弱点，记录在此，不在 v1 解决。

## 六、插件结构（草案）

```
<目录>\dsh-podbridge\
├── package.json          dsh.bundle / dsh.client 声明
├── cordis.patch.yml      插入 profile
├── index.js              Host 侧：绑定、鉴权、prompt/事件、HTTP+WS 服务
├── client.js             设置页（DSH 内部插件）：总开关、会话选择、配对码、在线数
└── src/
    ├── config.js         配置（自管 settings.json，不用 schemastery）
    ├── envelope.js       入站信封渲染 / 出站消息渲染
    ├── auth.js           token 生成/校验
    └── hub.js            WS 连接管理、补发
```

**没有 `web/`**：桥接不下发任何界面。聊天软件的 UI 在它自己的工程里。

### 6.1 配置项（草案）

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | false | 总开关 |
| `sessionId` | '' | 绑定的 DSH 会话，必填 |
| `listenPort` | 8787 | 自带 HTTP/WS 端口 |
| `authToken` | 随机生成 | 客户端配对用；在设置页可查看/重置 |
| `messageMaxChars` | 4000 | 单条入站文本上限 |
| `debounceEnabled` | true | 入站聚合总开关 |
| `silenceSec` | 6 | 静默窗口（秒），每条新消息重置 |
| `maxWindowSec` | 15 | 窗口总时长上限（秒） |
| `maxMsgs` | 10 | 攒满多少条立即投递 |
| `segmentMaxChars` | 2000 | 单个气泡的兜底长度上限 |

### 6.2 两套 HTTP 面（**必须分清**）

桥接同时暴露两个**互不相干**的接口面：

| 面 | 路径 | 使用方 | 说明 |
|---|---|---|---|
| **管理面** | `/api/dsh-podbridge/*` | **DSH 设置页**（本插件自带的 client 插件） | 配置、绑定、配对码、在线数、吊销 |
| **服务面** | `/pair`、`/socket` | **聊天软件** | 只实现《Pod 桥接协议 v1》，不涉管理 |

**桥接不提供任何 HTML/UI 给聊天软件**——聊天软件自带界面，桥接是纯服务端。

管理面接口：

| 接口 | 说明 |
|---|---|
| `GET /api/dsh-podbridge/config` | 读取配置与运行状态 |
| `POST /api/dsh-podbridge/config` | 保存配置（切换绑定时校验总开关已关） |
| `GET /api/dsh-podbridge/sessions` | 会话列表（过滤归档） |
| `POST /api/dsh-podbridge/pairing-code` | 生成一次性配对码 |
| `POST /api/dsh-podbridge/revoke` | 吊销全部客户端凭证 |

服务面（对客户端）见 **《Pod 桥接协议 v1》**，本文档不再重复帧定义。

### 6.3 解耦约束（硬要求）

| 约束 | 检验方法 |
|---|---|
| 桥接**不**下发 UI、不依赖聊天软件的任何实现 | 关掉聊天软件，桥接功能一切正常 |
| 聊天软件**不**依赖桥接存在 | 桥接未启动时，客户端仍能打开、看本地缓存、进设置、显示"未连接" |
| 两侧只通过《Pod 桥接协议 v1》交互 | 换一个客户端实现，桥接一行不改 |

### 6.4 `clientMsgId` 的去重

**保留它的主要理由**：防止客户端出现恶性 bug 时，**反复重发同一个 id** 把上下文迅速刷爆。
（每次都生成新 id 的刷屏由限流兜底：每 IP 每分钟 60 条。）

- 去重窗口：内存保留 1 小时
- 它**不是**内容指纹，**不会合并**文本相同的两条消息
- 你故意连发两次相同文本 = 两个 id = 两条消息，这是正确行为

## 七、非功能要求

| 要求 | 说明 |
|---|---|
| **幂等** | 同一 `clientMsgId` 的重复帧只投递一次（内存去重，保留 1 小时）；防 bug 循环刷屏 |
| **离线** | 手机断线期间会话照常跑完；重连后按 seq 补拉未送达的回复 |
| **顺序** | 同一会话的回复必须按顺序投递，不并发写 |
| **拒绝要说明** | 因总开关/绑定失效而拒收时，发一条 `role=system` 消息说明原因（不静默丢） |
| **不写坏会话** | 只用官方 prompt；失败即报错，不做降级写入 |
| **重启安全** | 插件重载后恢复绑定；参照 tick 的世代守卫思路，防止旧实例写回 |

### 7.1 已知限制：重启会丢缓冲

入站聚合的 6 秒缓冲**只存在内存**。如果插件在这 6 秒内被重载，缓冲里的消息会丢失，
而客户端**无从察觉**（没有回执机制）。

- 触发概率：低（重载通常由管理员手动触发）
- 表现：消息像没发出去一样，需要手动重发
- 为什么接受：引入回执/落盘会把协议和客户端状态机都复杂化，而收益只是覆盖一个极短的窗口

## 八、技术选型（已定）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 客户端形态 | **软件形式**：Windows = Electron（托盘常驻）；Android = 系统 WebView + 自写壳（含文件选择器、文件库、下载与通知的 JS 桥，不走 Capacitor）。**UI 内置在客户端里**（随包分发），桥接不下发界面——两者只按《Pod 桥接协议 v1》通信。不做 iOS |
| 2 | 网络接入 | 首选 **frp + 国内小 VPS**（稳定、自带 TLS）；次选 Tailscale 直连。**不做公网裸端口** |
| 3 | 推送 | **客户端可选开启，默认关闭**。Android 开启后需要前台服务（常驻一条"桥接运行中"通知）；Windows 用 Electron 托盘 + 原生通知。不依赖任何第三方推送服务 |
| 4 | 附件与图片 | v2 |
| 5 | 审批与提问通道 | v2 |
| 6 | 群聊（多 agent 房间） | 另立设计 |

### 8.1 推送为什么这样做

- 国内 Android 拿不到 FCM；WebView 不支持 Web Push
- 所以推送只能靠**客户端长连接 + 本地通知**：连接活着就能弹，连接断了就等重连补拉
- 客户端侧的实现细节属于客户端自己的文档，本插件只依赖协议

### 8.2 安全（个人软件量级）

| 项 | 决定 |
|---|---|
| 配对 | 设置页生成**一次性配对码**（6 位，5 分钟有效）→ 客户端换长期 token |
| 传输 | frp 提供 TLS；局域网可 HTTP |
| 权限 | 单用户、单身份；token 即身份，无角色矩阵 |
| 失败 | 401/403 一律不投递、不返回任何会话内容 |
| 限流 | 每 IP 每分钟 60 条入站，超出丢弃并记日志 |
| 吊销 | 设置页可一键吊销全部客户端凭证 |

## 九、可借鉴 / 不可照搬（来自 qqbot 与 qq-bridge 的经验）

| 借鉴 | 原因 |
|---|---|
| 会话级串行发送链 | 保证"先文字后状态"的顺序不被并发打乱 |
| 发送失败必须对调用方可见 | 旧实现静默 resolve，用户以为发了其实没发 |
| `requestId` 做幂等 | `prompt` 要求此字段；重发不能产生两条 |
| 一轮一推 + 状态收尾 | 与 QQ 的被动回复模型无关，是通用做法 |

| 不可照搬 | 原因 |
|---|---|
| `replyTarget {scope,targetId,msgId}` | QQ 被动回复模型独有 |
| `ReplyLimiter(4)` | 平台频控 |
| `openStream` 全量替换 | 我们不做流式 |
| `chunker` 按字节分片 | 长度约束语义不同 |
| `debounce` 消息聚合 | 一对一不需要 |
| `agent.followup + whenIdle` | 我们用 `prompt(queue)`，宿主排队 |
| `agents.create/resume` 自持 Agent | 只服务一个绑定会话，不需要生命周期管理 |

**关于分段提示的一个实现决定**

两难：`systemPrompt.section()` 在**调用者作用域**注册，插件在根作用域注册就污染所有会话；
但把说明塞进消息文本，**上下文压缩后会丢**，模型随后就忘了约定。

做法：**注册到绑定 agent 自己的 ctx**（`agent.ctx.systemPrompt.section(...)`），
只影响那一个会话；section **每一步重新装配，压缩不掉**。
拿不到 `agent.ctx`（会话没在运行）时，退回"本进程第一条投递附一次说明"作为兜底。

实测：日志出现 `分段提示已注册到绑定会话的系统提示`，投递文本里**没有**附加说明，
模型仍然按约定拆成了 2 条气泡。

**源码位置**

- 部署（DSH 读取）：`<目录>\dsh-podbridge`（profile 依赖 `link:` + node_modules junction）
- 工作副本（便于编辑）：`work_workspace/podbridge-stage`
- 部署方式：把工作副本整体复制过去，然后 `plugin_manager set_bundle` 关→开

**已知实现差异**：传输用 **SSE + POST** 而非 WebSocket——
profile 里没有 `ws` 包，link 安装的插件无法解析该依赖；协议语义不变。

## 十、验收要点（初版）

| # | 判定 |
|---|---|
| B1 | 绑定会话后，手机发消息能进会话，且 agent 能看到 `[chat]` 前缀与原文 |
| B2 | agent 的整条回复能回到手机，顺序正确 |
| B3 | 总开关关闭时消息被拒，手机收到提示，会话无新消息 |
| B4 | 切换绑定必须先关开关；切换后待投递队列为空 |
| B5 | 归档会话不出现在选择器 |
| B6 | 同一条消息重发（同 clientMsgId）只投递一次 |
| B7 | 手机断线期间回复不丢，重连后补到 |
| B8 | 插件重载后绑定与队列恢复正确，不重复投递 |
| B9 | token 错误时返回 401，不投递、不泄露会话内容 |
| B10 | 日志里能看到每次入站/出站的 id 与耗时，可用于事后追查 |
| B11 | 配对码只能使用一次，5 分钟后失效；用过期码换取凭证被拒 |
| B12 | 同一 token 同时连接两台客户端，消息两边都能收到（广播） |
| B13 | 客户端断开重连后，未送达的回复补齐且不重复 |
